# MAX30102-only follow-up — 27 October 2026

## Minimal-reader comparison and follow-up

Added the separate `max30102_bench` environment, excluded from the normal `esp32dev` source filter. It uses SparkFun 1.1.2's standard red/IR getters, with the same LED current, averaging, rate, width and ADC range as the application. Only its vendor default FIFO rollover behavior differs. Wi-Fi, API credentials and the other sensors are absent. It is a raw acquisition comparison, not an HR/SpO2 calculation.

The first 28-second capture produced 108 nonzero reports of 141, initially around red 149000 / IR 175000. After roughly 10 seconds, all register reads failed and values became zero. Therefore the combined Vyana application is not required for the intermittent failure. The vendor reader does not verify every FIFO transaction; its numeric output alone is not proof of valid samples.

A second 43-second capture produced 531 nonzero, unsaturated reports. It ran at 100 kHz for 15 seconds, then restarted the controller at 50 kHz for the remainder. Checked ID transactions mostly returned ESP_OK and 0x15 with SDA/SCL high; one earlier ID read returned 0xff despite ESP_OK. Since the initial phase was also delivering raw values, the capture does not establish that lowering clock speed fixed the cause.

Added a configurable MAX30102_I2C_HZ (default 100000, allowed 10000-400000). This private bench configuration currently selects 50000. Restored normal Vyana firmware, matching the vendor's individual checked configuration/pointer transactions and STOP before FIFO reads. A later capture initialized correctly and had no transaction errors, but repeatedly reported pointer/overflow state 00/1f/00 with no samples. Added bounded overflow recovery that pops and discards a complete old frame before clearing FIFO; no discontinuous sample is accepted into a measurement window. A regression test covers a sticky overflow counter that clears on a frame pop, as described in the manufacturer data sheet.

All 43 native tests passed after the final recovery change. Normal firmware build/upload and hash verification succeeded. The subsequent warm-reset capture detected/configured the MAX but still showed 00/00/00 pointers and zero raw readings. Fresh optical measurements in the full application remain unverified. Wi-Fi/API 200 delivery was restored with the existing hotspot settings. A complete external power cycle was requested because resetting the ESP32 leaves the sensor powered. No defective-part conclusion is supported by these captures.

Captures: ignored `.audit-runtime/esp32-setup/max-minimal-vendor.log`, `max-minimal-slow-retry.log`, `max-vyana-restored-boot.log`, `max-vendor-transactions-vyana.log`, and `max-overflow-recovery-vyana.log`.

After the user confirmed a full 10-second external power-off and USB reconnection with only MAX attached, the 22-second capture again showed zero raw values and no valid measurements. Counters reached 1051 invalidations, 23 short reads and 2068 clear failures, with one rejected pointer value; the last failure was FIFO-clear register 0x04, Wire code 4. HTTP 200 delivery continued. Cold power cycling did not resolve the full-application failure. A direct-versus-breadboard wiring isolation question remains for the next bench step. No heart rate or SpO2 has been validated in the full firmware.

The normal firmware is restored with the private 50 kHz bench setting. It retains short-read, saturation, overflow, contact, age and fresh-window validity checks. Config/pointer accesses use checked single-register reads, FIFO pointer clearing uses individually checked writes, and FIFO_DATA selection uses the vendor's STOP transaction pattern. These changes and the bounded overflow-frame discard passed 43 native tests, but they have not established reliable operation on this physical setup. No fake replacement values are sent to the API.

Reference: [SparkFun Basic Readings example](https://github.com/sparkfun/SparkFun_MAX3010x_Sensor_Library/blob/master/examples/Example1_Basic_Readings/Example1_Basic_Readings.ino) and [MAX30102 data sheet](https://www.analog.com/media/en/technical-documentation/data-sheets/MAX30102.pdf), FIFO behavior on pages 13-15.

## Earlier diagnostic capture

The user disconnected AD8232 entirely and connected only MAX30102 to the ESP32, powered from computer USB on COM3. This test does not involve body-connected ECG electrodes.

Startup now detects address 0x57 and part ID 0x15, with configuration FIFO=0x4f, mode=0x03 and SpO2=0x27. This differs from the earlier no-response state. A 33-second capture nevertheless reported red/IR zero, invalid measurements and 1055 combined driver errors. The combined counter alone did not identify their cause.

Added serial-only diagnostic fields without changing acquisition policy or API payloads. They distinguish failed register-address writes, short reads, empty buffers, invalid pointer values and failed FIFO-clear writes. Existing sensor tests now also assert the read-failure diagnostics. All 42 native tests passed; ESP32 build/upload and flash hash verification succeeded. The board emits complete diagnostic JSON without an overflow warning.

The subsequent 26-second hardware capture reached 27 short reads (last returned byte count 0), 87 failed FIFO-clear writes (last Wire error 4, generic other error), zero rejected pointer values and zero empty-buffer reads. Red/IR remained zero, FIFO pointer snapshots were 00/00/00, and neither HR nor SpO2 became valid. Counters measure different operations and are not expected to sum to the combined invalidation counter. Wire repeated-start register-address writes defer the actual transfer to requestFrom on this ESP32 core, so a zero tx_errors field does not establish successful bus transactions.

Conclusion: register reads/FIFO-clear transactions are failing; this is not solely an algorithm validity or finger-contact rejection. The underlying electrical versus controller/firmware cause remains undetermined. No claim of a defective sensor, wrong voltage or loose wire is established. The next bench work is to isolate the four-wire power/I2C path and compare against a minimal vendor sample before replacing parts. Credentials and private configuration were preserved.

Local captures are in ignored `.audit-runtime/esp32-setup/max-only-reconnected.log` and `max-error-stages.log`. Stage codes: 1 register-address write, 2 short read, 3 empty read buffer, 4 invalid pointer bits, 5 FIFO-clear write. Register/code/received-byte fields describe their respective failure operations and retain the last recorded values.
