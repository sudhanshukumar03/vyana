# AD8232 code review 28 October 2026

## Result

The review did not identify a firmware cause for the previously observed
80–85% raw ADC clipping. It found and corrected one diagnostic inconsistency:
the wireless bench re-read lead GPIOs after the driver had acquired the raw
sample. A changing lead input could therefore be reported with a different
state from the driver's cached combined status for that observation.

The driver now retains both individual lead bits on every accepted poll, reads
both even when LO+ is HIGH, and derives the combined status from those values.
Both standalone bench programs report this cached snapshot. This associates
metadata with one acquisition attempt; it does not claim the digital inputs
and ADC conversion occur at exactly the same instant. ADC values, attenuation,
sampling target, clipping thresholds, API payload schema and rhythm policy were
not changed. No filtering or generated waveform was added.

## Findings checked

- The driver uses OUT on GPIO34, LO+ on GPIO35 and LO− on GPIO32. The two lead
  pins and ADC pin are inputs. Raw conversion is configured for 12 bits and
  per-pin ADC_11db attenuation. GPIO34 is an ADC1 input on the ESP32 used here.
- There is no SDN GPIO assignment, pinMode or digitalWrite in the AD8232 driver
  or standalone firmware. Earlier mandatory external-SDN wiring advice was a
  documentation error, corrected separately. The SparkFun board already has
  the R15 10 kΩ pull-up; other breakout revisions need their own schematic.
- Either digital lead indication HIGH produces `Leads Off`. Both LOW produce
  `Unknown`, not a diagnosis of normal rhythm. Acquisition still retains the
  raw ADC value for troubleshooting even when a lead-off indication is active.
- analogRead and analogReadMilliVolts perform separate conversions. The pinned
  Arduino core source was inspected; the millivolt estimate is not a calibrated
  conversion of the very same saved raw sample. Documentation already states
  that distinction. The wireless trace transports raw ADC samples only.
- The wireless acquisition task and HTTP transport are separated by a locked
  sample ring. Each response copies a batch briefly under the mutex, then
  serializes outside it. Ring sequences, cursor/reset handling and overflow
  disclosure preserve visible gaps rather than inventing intervening samples.
- The normal app receives an ECG summary; its illustrative waveform is separate
  from the standalone bench's actual raw trace. No QRS/rhythm classifier is
  implemented. Missing classification does not explain rail-clipped ADC input.

## Validation and deployment boundary

All 60 native tests across six suites passed, including a new regression that
changes lead inputs between polls and checks that the previous raw observation
retains its cached lead state until the next eligible acquisition. These tests
use mocked hardware and do not validate a real ECG.

Build-only verification succeeded for all three targets: `esp32dev`,
`ad8232_bench` and `ad8232_wifi_bench`. Main firmware flash use was 96.4% of the
configured application partition; standalone USB and wireless builds used
23.0% and 82.4%. Existing third-party library warnings in the main build were
not changed during this AD8232 review.

**The correction has not been uploaded or physically validated.** The last
verified uploaded image was preserved locally before rebuilding, and the
candidate binary hashes are recorded separately in
`artifacts/ad8232-check-2026-10-28/code-review-validation.json`. Previous body
captures therefore belong to the earlier flashed firmware. They cannot be
reported as validation of this source correction, and a metadata consistency
fix cannot be claimed to recover an already clipped waveform. Upload would
require pads off the body before reconnecting computer USB.
