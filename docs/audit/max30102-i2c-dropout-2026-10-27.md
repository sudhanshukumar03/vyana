# MAX30102 intermittent I2C failure — 27 October 2026

## Scope and observed error

Only MAX30102 connected directly to ESP32 D21/D22 over jumper wires, powered
through laptop USB on COM3. AD8232 removed. All-sensor `esp32dev` remains the
default target; MAX-only tests are selected explicitly. No wiring, supply,
LED current, sample rate, averaging or I2C clock changes were requested here.

The prior FIFO overflow-loop fix restored raw acquisition. The next failure
was a separate, intermittent I2C transaction failure, followed by discarded
measurement windows and sometimes failed initialization. Enabling Arduino
error logging in the explicit `max30102_bus_diag` target captured:

```text
i2c_master_transmit_receive failed: [259] ESP_ERR_INVALID_STATE
i2cWriteReadNonStop returned Error 259
i2c_master_transmit failed: [259] ESP_ERR_INVALID_STATE
```

Framework: Arduino-ESP32 3.3.12, installed ESP-IDF headers 5.5.5. PlatformIO
framework build defines `CORE_DEBUG_LEVEL=0`, so the diagnostic environment
must remove that flag before setting level 1. Binary/object inspection
confirmed error strings compiled in; upload/hash verification succeeded.

The SDK error identifies a failed transaction, not a proven damaged sensor,
loose wire, or unique underlying cause. The matching SDK's synchronous path
can return INVALID_STATE when transaction status is not DONE. No electrical
trace or voltage measurement was available. See [Espressif source](https://github.com/espressif/esp-idf/blob/v5.5.5/components/esp_driver_i2c/i2c_master.c).

## Changes and verification

1. On initialization retries only, end/restart Wire at the same D21/D22,
   configured clock and 20 ms timeout. Ordinary `Wire.begin()` on an existing
   bus does not recreate the controller. Preserve cumulative counters, check
   end/begin results and require a new optical window. The existing three
   failed FIFO clears / two-second initialization backoff remains bounded.
   [Arduino API documentation](https://docs.espressif.com/projects/arduino-esp32/en/latest/api/i2c.html#end)
2. Limit FIFO checks to every 10 ms while draining all pending frames. The
   previous per-loop checks created unnecessary empty transactions at a much
   higher rate than the effective 25 sensor frames/second. The main loop and
   other sensor cadence are unchanged.
3. Expose controller restart/failure counters in serial diagnostics. Stage 9
   reports end failure (code 1) or begin failure (code 2). Invalid/stale values
   continue to be withheld; no generated vitals were added.

The first change alone did **not** eliminate hardware failures. One test
needed nine initialization retries before raw acquisition resumed; it had
no detected finger after that point. A later finger-contact run still had
five acquisition/recovery errors. Do not describe controller restart alone
as the verified root-cause fix.

After adding bounded polling, 55 consecutive one-second reports, uptime
13,375–67,375 ms, all showed detected contact, calculated HR and SpO2,
zero I/O errors, zero recovery attempts, one initialization and zero bus
restarts. Accepted-frame count increased by exactly 1,350 across 54 seconds
(25 frames/second). HR output varied 60–166 BPM; SpO2 output was 99–100%.
These are algorithm outputs, not validated physiological measurements.
This short success does not prove the original trigger or long-term stability.

55 native tests passed across five suites, including queued-frame preservation
under bounded polling, controller stuck until end/begin, failed end/begin,
bounded retries, fresh-window gating, FIFO overflow and all-sensor firmware
JSON behavior. Full `esp32dev` build passed: 87,040 static RAM bytes and
1,263,908 flash bytes. It was not uploaded during MAX isolation.

A temporary diagnostic-only ACK/STOP identity probe was not reached during
the later acquisition errors and provided no additional evidence. It was
removed. The explicit diagnostic target retains only controller logging.

## Evidence and limitations

Ignored `.audit-runtime/esp32-setup/` captures:

- `max-bus-detailed`: first detailed 259 failures, I/O errors 0→11.
- `max-bus-before-recovery`: finger-contact failures, errors 11→18.
- `max-bus-restart-test`: controller restart alone did not cure startup failure.
- `max-bus-ack-test`: five errors despite controller-restart capability.
- `max-bounded-poll-test`: 55 reports and 1,350 new frames, no errors.

The regular `max30102_bench` build without diagnostic logging was then uploaded
and its flash hash verified. A separate 55-report capture, uptime
25,372–79,372 ms, showed continuous contact and calculated HR/SpO2 with zero
I/O errors, zero recovery attempts and zero controller restarts. It accepted
another 1,351 frames across 54 seconds (approximately 25/second; report timing
can straddle a frame boundary). Final output was HR 75 BPM, SpO2 99%,
red 197,443 and IR 217,554. HR varied during the run; accuracy is unvalidated.
Evidence: `max-regular-final-test.json` and `.log` in the same ignored directory.
The ESP32 is left running this regular MAX-only firmware, not the diagnostic
or all-sensor firmware. Both post-polling-change captures passed; this is
short-duration evidence, not proof of an exclusively software/electrical root cause.
All-sensor physical operation and Vyana delivery remain outside this test.
