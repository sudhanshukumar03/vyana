# MAX30102 code fixes — 27 October 2026

Scope authorized after the read-only review: fix the identified software issues before a later hardware test. Current physical setup is MAX30102 only, connected directly to ESP32 by jumpers, ESP32 connected to this laptop over USB. No serial port was opened, board reset, firmware uploaded or wiring changed in this code-fix step. Previous physical captures are historical and do not validate this revised firmware.

## Changes

- Default PlatformIO target remains the all-sensor `esp32dev` system. Temporary MAX-only troubleshooting explicitly selects `-e max30102_bench`, which compiles only the standalone entry point and local optical algorithm with Wire/SparkFun dependencies. The user clarified that isolation is only a test stage; the final system retains all sensors together.
- The standalone program uses fixed D21/D22 pins and 100 kHz, without private configuration, credentials, Wi-Fi, other sensor drivers, automatic clock changes, reversed-pin probes or unrelated address scans.
- Initialization failures retry every two seconds. Checked part ID and register configuration are required; retries preserve counters, discard old raw/window data and cannot publish a stale calculated result.
- Acquisition faults invalidate the window immediately. FIFO recovery attempts one clear per 100 ms without recursively clearing twice. Three failed recovery attempts switch to the initialization retry path.
- Each last-error snapshot resets its register, Wire code, received/expected byte counts and value together. Stages distinguish read, pointer, reset, identity, configuration and vendor-init failures. Counters separately track initialization and recovery.
- Standalone serial JSON reports raw light values separately from calculated HR/SpO2. Each calculated field is null unless its own algorithm flag, physical range, contact and freshness checks pass. One unavailable metric does not hide a valid other metric. Full Vyana's combined-vitals API policy is unchanged.
