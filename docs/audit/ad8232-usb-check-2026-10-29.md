## Code review and ADC initialization-order correction

At the user's request, the AD8232 driver, USB and wireless benches, sample ring, viewer and local proxy were reviewed against the captured data and pinned Arduino-ESP32 3.3.12 core implementation. No wiring change, board reset, upload or new body recording was performed during this review. The existing pin assignments, active-HIGH lead-off logic, 12-bit raw range, input-only GPIO configuration and 4 ms sampling target agree with the relevant device interfaces. The acquisition path retains actual raw input even during lead-off; neither the sample ring nor viewer rescales it into 0 or 4095. No ADC value replacement or waveform simulation was found in this path.

One startup-order defect was identified in `initAD8232()`: it called `analogSetPinAttenuation()` before any ADC conversion had attached GPIO34 to the core's oneshot ADC channel. In the pinned core, the per-pin configuration path checks that registration and otherwise logs that the pin is not configured as an analog channel. The call is therefore ignored on first initialization. The driver now performs and discards one setup `analogRead()` after selecting 12-bit resolution, then applies the pin attenuation. This setup conversion does not enter the published sample stream or summary counters.

This is not an established explanation for the recorded clipping. The pinned core already defaults to `ADC_11db`, the same attenuation requested by the driver; its first normal read previously attached the channel using that default. GPIO34 is an ADC1 input, and the earlier known-ground and known-high checks demonstrated basic input response. Native tests do not validate real electrode contact, module supply voltage, SDN bias, ADC electrical behaviour or waveform quality. The core's raw-read wrapper also does not expose the low-level oneshot return code to this driver, so these checks do not independently exclude ADC read errors.
